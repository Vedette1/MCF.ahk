# MCF (MCode Forge)

MCF is a COFF linker implemented in AutoHotkey v2 and partially in C / C++.  
It is designed to build position-independent machine code (MCode) directly into memory.

![Screenshot](https://github.com/Vedette1/MCF.ahk/blob/main/screenshot1.png)

## About the Project

MCF is a COFF object file linker tailored for generating MCode (an in-memory machine code loader).  
It is compiler-agnostic: it accepts standard `.o` / `.obj` files generated by C, C++, Zig, or any other language capable of producing COFF binaries.

Its primary goal is to combine one or more object files into a single contiguous block of machine code with resolved relocations and an exported symbol map, ready to be called via `DllCall`.

Please note that MCF is developed primarily with **GCC** in mind. Although the COFF specification is strictly defined, different compilers have their own quirks and specific behaviors, which means some code might not link properly if compiled with MSVC, for example.

Also keep in mind that MCF is not omnipotent and is far from a full-fledged linker like `ld.exe`. Nevertheless, MCF can successfully link ~95% of C code without any source modifications, as well as ~10% of C++ code.

## Architecture

The linker aims to emulate the behavior of standard linkers (`ld`, `link.exe`, etc.), but instead of building a PE/ELF executable, it outputs a contiguous buffer of machine code.

Key stages:
- Parsing COFF headers, sections, and the symbol table;
- Building memory layout taking alignment into account;
- Applying internal and external relocations;
- Generating a compact IAT (Import Address Table) tail for dynamic imports;
- Exporting symbol and section offset maps.

## Graphical User Interface (GUI)

The project includes a GUI that combines:
- Linker configuration settings;
- Symbol tables with name demangling;
- COFF file inspection/information;
- Build and operation logs;
- Compiler wrappers (one-click `compile → obj → MCode` workflow);
- A simple text editor with basic syntax highlighting;
- Tools for working with static libraries (`.a` / `.lib`): object file extraction and symbol searching.

The GUI is completely optional — the linker can also be used programmatically (as a library).

## Example

```ahk
/**
#include <windows.h>
int msgBox() {
	return MessageBox(0, "Hello Mcode", "Title", 0);
}
*/
; compiler : TDM-GCC 10.3.0
; flags    : -m64 -O2 -fPIC -fno-stack-protector -fno-plt -fno-asynchronous-unwind-tables

offset := Map()
offset["msgBox"] := 0x0 ; 2
offset[".text"] := 0x0 ; 4 [dispensable]
offset[".data"] := 0x20 ; 6 [dispensable]
offset[".bss"] := 0x20 ; 8 [dispensable]
offset[".rdata"] := 0x20 ; 10 [dispensable]

ptr := GetMcodePtr("4531c94c8d0516000000488d151500000031c9ff2500000000909090909090905469746c650048656c6c6f204d636f6465000000000000000000000000000000|User32:MessageBoxA:21:4") ; Copy the GetMcodePtr function from the GUI.
DllCall(ptr, "int")
```
## Current Limitations
- SEH (Structured Exception Handling) — `try / catch` is not supported. Implementing this would require registering exception tables `(.pdata / .xdata)`, which is not planned in the near future.
- Thread Local Storage (TLS) — Not supported and most likely will not be implemented, as it is extremely complex.
- COMDAT — `IMAGE_COMDAT_SELECT_LARGEST` and `IMAGE_COMDAT_SELECT_ASSOCIATIVE` selection strategies are not implemented.
- Global Constructors / Destructors — Sections such as `.CRT$XCU, .init_array, .ctors`, and similar are not processed. Code that is supposed to run before/after the entry point will not be executed.
